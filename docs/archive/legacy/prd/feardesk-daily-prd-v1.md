# FearDesk 日报更新产品需求文档

版本：1.1。日期：2026年10月3日。状态：PRD已确认；已纳入用户接受的每小时恢复临时方案，进入模块架构评审。

设计方案及流程图已获用户确认“设计通过”。本文将已通过的方案展开为产品规则与验收要求，供产品评审使用；PRD通过后才进入技术方案评审、架构设计和编码。本阶段只更新规格与架构；产品编码按既有授权在架构评审后进行。本轮不部署生产、不发送真实飞书、不修改每日生成频率。

## 1 背景与目标

用户需要随时读取已保存日报，也需要主动获取最新可用已收盘交易日的数据。当前操作把数据更新、快照生成及飞书投递串在一个同步请求里，遇到中断会留下running，页面难以区分“读取没成功”“生成没完成”和“消息没送达”。

本次改造的目标是形成可独立理解的三件事：读取已保存日报、生成并保存新日报、向飞书投递指定日报。刷新不产生业务写入；手动生成不受北京时间14点门禁限制，默认不发飞书；定时生成不依赖网页打开。每份日报明确交易日、生成时间及完整性，每个任务显示进度和终态，飞书单独显示接收结果。

成功判据：用户能在任务运行中继续读取旧日报；请求断开后任务能够继续或恢复；相同输入并发触发只有一个有效生成执行和一份正式快照；失败不替换旧完整日报；飞书结果不确定时不盲目重发。

## 3 范围和阶段边界

P0范围包括只读刷新、手动生成、独立云端定时生成、网页只读自动检测、分离状态、过期任务恢复、部分数据处理、并发去重、不可变日报及验收可观测性。这些是一个完整范围，不把恢复或去重留作上线后的补丁。

本轮不涉及IV Rank、期权数据、PCR补完、恐慌公式重设计、新行情供应商、观察池管理重设计、账号或站点权限调整。原有独立飞书发送能力可保留，但本次不新增发送快捷入口、批量补发或历史消息自动补发。历史冻结日报正文不得被覆盖。

流程固定为：已通过设计方案和流程图 → 本PRD评审 → 技术方案评审 → 架构设计 → 编码与验证。设计获批不等于PRD获批，也不授权下一阶段自动部署。

## 4 用户操作与页面结构

日报列表页提供两个明确操作：次按钮“刷新日报”，主按钮“立即生成最新日报”。原“运行每日更新”必须换成清晰的手动生成语义；原“生成卡片预览”不能继续占用刷新入口。若保留单独预览工具，应清楚说明其是否会保存，不能伪装成只读刷新。

页面上方先展示当前正式日报，其次展示本次请求及最新活动任务。生成中的任务不得挡住当前报告。无报告但有任务时展示空态与进度；读取失败展示读取失败，不能把数据库无法读取误报为无日报。

| 区域 | 必须展示 | 规则 |
|---|---|---|
| 当前日报 | 美国交易日、生成北京时间、版本、行情完整性 | 时间取已保存快照，不取本次刷新时间 |
| 评分覆盖 | 有效评分数与观察池总数、预热数、前日可比数 | 行情齐全不等于评分全部有效 |
| 新鲜度 | 最新应有交易日、最新可用交易日、日期落后原因 | 不用“今天”替代美国交易日 |
| 生成任务 | 来源、任务ID、状态、阶段、开始和更新时间、结果 | 任务与报告通过ID关联，不能按列表第一行猜关联 |
| 飞书投递 | 本次请求是否授权发送、报告投递状态和来源 | 手动未发送与定时已发送可同时为真 |
| 历史列表 | 按交易日和有效修订版本排列、冻结链接 | 打开历史页不自动替换正文 |

示例文案：“当前日报：美国交易日2026-10-01；生成时间：北京时间2026-10-02 14:08；行情齐全；有效评分43/46，预热3；本次手动请求未请求发送；该报告飞书投递：未请求发送”。例子仅解释展示结构，不代表该日真实日报存在。

### 4.1 刷新日报

FR01：任何时刻均可触发只读刷新，包括生成中、飞书发送中、14点前、周末或休市。刷新只读取已保存报告与状态，不抓行情、不计算、不初始化业务数据、不创建报告或任务、不发送飞书。读取接口不得借“恢复过期任务”产生写入。

刷新按钮仅在自身读取中显示“读取中”，生成busy不能禁用它。连续刷新可合并或取消旧读请求；旧响应不能覆盖新响应。成功后显示最后检查时间；失败保留已加载内容并显示读取错误、重试入口，不能用空态覆盖旧内容。

### 4.2 立即生成最新日报

FR02：已授权用户点击后，服务端持久化请求并受理生成，返回可追踪的任务ID。按钮显示“任务已受理”，而不是立即显示“日报已生成”。受理完成后页面可以关闭；重新进入能找到相关任务和结果。临时执行器可能在有边界的初始分片后等待后台续跑；“立即生成”表示立即受理启动，不表示全部工作即时完成，页面须明确等待状态。

FR03：手动生成没有14点门禁。服务端决定交易日、观察池及算法版本，客户端不得指定任意历史日期、任意标的或机器人地址。纯手动生成即使全局自动发送启用，也不触发飞书。

FR04：同一次点击的网络重试沿用同一请求身份；重复点击、多个标签页或手动与定时相遇时，共享同一兼容活动任务。新观察池或新算法输入不强行合并，可排队为新的生成任务，并显示等待原因。

### 4.3 定时自动生成

FR05：生成由独立云端触发，网页关闭、电脑休眠或用户未在线不影响触发能力。定时与手动共用生成规则、完整性校验及防重复规则，但来源和投递意图分别保留。

现状背景为北京时间周二至周六14/15/16点；周一至周六14点仍为候选。PRD不选择其中一种作为已批准调度。15/16点若最终定位为重试，必须明确受理或恢复未完成生成任务；只GET查状态不能算重试。休市不制造新交易日，也不凭定时触发自动补发历史消息。

### 4.4 网页自动检测

FR06：页面可见且无活动任务时，每30秒读取轻量状态；有相关活动任务时每5秒读取；隐藏标签暂停周期请求。重新可见、网络恢复、重新进入页面时立即读取一次，不触发生成。任务结束后回到30秒周期。

当前日报ID或修订版本变化后，列表页读取并展示新保存的完整报告。历史页只提示“有新日报”，不更换冻结正文。一次轮询失败保留已有内容；持续失败显示“自动检查暂不可用”，用户仍可手动刷新。轮询响应倒序、多个标签页及恢复网络均不得触发业务写入。

## 5 交易日与数据新鲜度

FR07：最新应有交易日是按美股交易日历、纽约时区、正常或提前收盘判断的最近已结束交易日。最新可用交易日是行情源能提供的最新有效已收盘SPY日线日期。未收盘当日、盘后未确认的日线、未来日期均不能成为报告目标。

SPY是共同日期基准，不是完整性的替代品。选定可用目标日后，所有冻结观察池标的必须验证同日行情；不能拿SPY当日、个股前日拼在一起。前一交易日按有效交易日期确定，不能简单减一个自然日。

| 情况 | 用户可见结果 |
|---|---|
| 最新可用日等于最新应有日且截面齐全 | 保存或复用正式日报，显示最新应有日已完成 |
| SPY源延迟，可用日早于应有日 | 可校验并保存该可用日完整日报，或复用已有同内容日报；显示日期落后，不宣称应有日已完成 |
| SPY目标日存在，但个股缺目标日 | 本次任务部分数据不足，不发布；保留上一份正式日报 |
| 周末、节假日或尚未收盘 | 选最近真实已收盘日；同内容复用，显示“无新收盘日线” |
| SPY完全无可用数据或返回日期异常 | 明确失败，记录原因，不生成伪日报 |

不得为了让任务看起来成功，在个股缺数时自动从目标日退到更旧共同日期。允许的“源延迟旧日结果”必须由SPY可用日确定并显式标示落后，不能把旧报告重新改日期或刷新生成时间。

## 6 完整性与部分数据规则

FR08：发布条件必须同时满足下列要求。观察池非空；SPY和所有冻结标的有目标日有效日线；OHLCV有限且合法、价格为正、成交量非负、high不低于open/close/low、low不高于open/close；没有重复目标日期或待核对异常；计算输入和算法版本一致；财报变更引发的必要重算已完成。

评分预热单独处理。新股历史不足且score/total为空，只要目标行情及计算状态合法，可以发布“行情齐全、部分评分预热”的报告；不能用0替换null，不纳入有效评分均值，显示覆盖率。前日数据不足只影响比较样本和变化值，不能伪造涨跌或补成0。

财报日期未知、官网访问失败或使用有效缓存，不单独使行情不完整；须显示来源、预计或已确认、查询错误与待核对状态。人工纠错优先；来源失败不能抹掉已保存的有效未来日期。财报修正延续现有当时可知规则，不借此次改造改算法。

FR09：数据不足时保存任务诊断，包括目标日、阶段、失败和缺失标的、可否重试及重试计划。允许在任务详情展示诊断内容，但本轮不新增不完整正式日报；已有历史不完整预览仍可按历史入口查阅。任务失败不能修改旧冻结日报或当前完整日报指针。

## 7 状态与时间字段

为避免任务成功掩盖日期落后，生成状态、阶段和数据新鲜度是三个独立字段。正文中的状态值是产品语义，不规定数据库列名或具体接口格式。

| 生成状态 | 含义 | 可发生的下一步 |
|---|---|---|
| 排队 queued | 请求已持久化，尚未开始 | running；受理基础失败必须明确反馈 |
| 运行 running | 有有效执行者推进，显示阶段与进度 | ready、reused、partial、retry_wait、failed、interrupted |
| 等待重试 retry_wait | 可重试问题已记录，并有明确下次尝试 | running；达到上限为failed或partial |
| 中断待恢复 interrupted | 前次执行失去有效心跳或租约 | retry_wait；不能永久处理中 |
| 完成 ready | 通过校验并保存新的正式版本 | 终态，不受后续飞书失败影响 |
| 已复用 reused | 输入内容未变，返回既有冻结报告 | 终态，原生成时间不变 |
| 部分不足 partial | 数据不足且恢复预算耗尽或不可自动补齐 | 终态，允许用户发起新请求重试 |
| 失败 failed | 永久错误或任务时长、尝试预算耗尽 | 终态，显示原因和允许的后续操作 |

页面必须可区分确定交易日、同步SPY、同步观察池、更新财报、计算、校验、保存这些阶段。阶段的具体编排及必要重复计算留技术评审，必须先确认输入并校验完成后再发布。重试可从已验证的检查点继续；存在输入修订则失效检查点重新计算。阶段不能作为已经保存报告的证据。

必须记录请求时间、开始时间、最近进度时间、完成时间、报告首次生成时间。页面读检查时间单列。报告首次生成时间在复用时保持不变，任务完成时间可以更新。所有显示时间标明北京时间，交易日始终是美国日期；存储时间格式留技术评审。

新鲜度状态为最新应有日已完成、日期落后、无新收盘日线或待核对。ready/reused同时日期落后是合法组合，文案必须说清楚返回的是哪个交易日。

## 8 中断恢复与失败处理

FR10：任务受理持久化后，原浏览器关闭、HTTP断开或原执行者退出，不得成为任务永久running的理由。独立恢复过程检查活动任务，不由读接口或页面轮询承担恢复动作。

恢复时结束并保留前次尝试记录，给同一逻辑任务分配新尝试。每次写入和最终发布都必须由当前有效执行者完成；旧执行者复活不能覆盖新报告、终态或当前指针。恢复不得把飞书sending/unknown当作可自动重发。

下表为v1.1验收基线。用户已明确接受“每小时检查并续跑，恢复时间可能延迟”的临时方案；取消原60秒恢复及受理后30分钟墙钟终态承诺，保留有限执行预算与防重复。它不是已配置生产调度，也不承诺最多一小时恢复。

| 参数 | 提议目标 |
|---|---|
| 请求受理和只读状态响应 | 在46只观察池验收环境中，P95不超过2秒，不包含后台生成耗时 |
| 失去执行者的判断 | 120秒租约/无有效进度是失效判断基线；读接口只显示派生的待恢复提示，持久化接管由后台检查执行，不承诺120秒内巡检到 |
| 独立恢复 | 每小时扫描并续跑已存在的queued/retry_wait及租约失效任务；实际触发可能延迟，无恢复时间上限承诺；空扫描不生成、不发送 |
| 自动失败尝试上限 | 每逻辑任务最多3次因失败/中断而产生的执行尝试，含首次；正常分片交接不消耗失败次数，fragment领取次数单独审计 |
| 退避基线 | 30/120秒为最早允许重试时间，不保证届时执行；实际在后续后台检查中推进，限流提示可延后 |
| 总执行预算 | 累计实际执行时间最多30分钟，排队和等待小时唤醒不计入；异常退出按已预留分片预算计费，耗尽后禁止迟到发布。此项是有限工作预算，不是墙钟完成SLA |
| 页面发现新报告 | 健康网络下，正常页面30秒检测周期加一次读取耗时；活动任务页面5秒周期加一次读取耗时 |

网络错误、源临时不可用、限流、目标日延迟可在预算内重试；日期非法、权限拒绝、观察池为空等不能无意义自动重试。单个标的失败必须记录，不能静默用旧日行情替代。超过失败次数或累计执行预算要落终态，继续保留旧日报，并提供“重新生成”操作创建新的可追踪请求。

受理事务必须同时保存可被小时扫描发现的任务和请求关联；无需依赖即时派发成功避免永久丢失。正常分片交接保留检查点，并显示等待后台续跑；失效执行者的接管保留失败尝试与租约历史。恢复入口不创建新的日目标、不新增发送授权，也不直接调用飞书。生成已经落库而响应断开时重试，应关联同一已保存结果；若终态写入失败，恢复过程应从已保存发布事实修复状态，不能再次投递或制造第二份相同报告。

## 9 并发幂等与发布顺序

FR11：同目标日、同冻结观察池、同算法和同业务输入版本的活动生成任务合并。不同请求身份和触发来源分别保留，可指向同一任务。请求幂等与业务快照去重是不同层面的要求，都必须满足。同一请求身份的网络重试包括终态后重试，返回原任务结果；用户明确点击“重新生成”时才创建新的请求身份和尝试预算，仍需合并兼容活动任务，已有相同业务报告继续复用。

报告业务指纹涵盖交易日、有效行情与评分、实际参与报告的财报业务信息、观察池、算法和卡片格式版本；临时同步状态、心跳、查询时间及进度不能使相同业务内容变成新报告。输入无实质变化时复用报告ID及生成时间；行情修订或实际财报业务内容变化形成新冻结版本，不覆盖历史正文。

FR12：发布成功必须同时满足报告已保存、任务已关联结果和当前指针更新规则。用户不能看到“已完成”却查不到报告。具体事务与存储实现留架构设计。

当前日报按美国交易日优先，同日按服务端可比较的有效输入修订顺序选择，不按完成时间或created_at选择。旧交易日恢复晚完成只保存历史；同日旧输入晚完成也不能使当前指针倒退。无法确定输入版本先后的冲突必须显式待核对或基于最新输入重新生成，不选择随机胜者。

生成期间观察池或财报被人工改动，本次冻结范围保持可追溯；必要时以新输入重新排队，不把新旧输入拼成一个报告。全量行情同步、单标的同步及预览工具也必须遵守发布一致性规则，不能绕过防重复或生成混合截面。

## 10 飞书独立状态与授权

FR13：手动请求固定记录“不请求发送”，纯手动生成无论全局发送配置如何都不发消息。生成任务合并不合并发送授权：只有独立定时触发及其既有启用策略可以授权共享报告投递，与手动或定时谁先到无关。

页面同时显示本次请求意图和该报告实际投递结果。例如“本次手动请求：未请求发送；报告投递：由定时任务已发送”。手动动作不得扩大、取消或继承定时授权；定时授权也不得被展示成手动点击发送。

| 飞书状态 | 用户含义 | 自动重发规则 |
|---|---|---|
| 未请求发送 | 本次请求无投递意图或策略未启用 | 不发送 |
| 发送中 | 投递已提交或正在处理 | 不重复提交 |
| 已确认接收 | 飞书返回明确成功 | 同日报不重复提交 |
| 明确失败 | 接收端明确拒绝或可确定未接收 | 仅按已有独立发送能力及权限处理，不由生成重试擅自发送 |
| 结果不确定 | 网络中断或无法判断接收 | 禁止盲目重发，提示人工核对 |

飞书失败不会把生成ready改为failed。发送只使用已保存且符合发送要求的冻结报告；不完整数据不得自动发送。投递没有端到端恰好一次保证，不把“sending超时”简单改failed后重发。跨同日修订版本的自动补发继续保留现有抑制基线，新的修订补发政策不在本轮批准。

## 11 权限 数据保留与可观测性

FR14：网页读写保留既有身份边界与同站写入保护；云端服务入口保留独立授权与启用开关。客户端不能覆盖机器人地址、绕过日期规则或提交任意执行身份。失败提示和日志均不得出现Webhook、签名密钥、服务令牌或其他凭据。

FR15：每次请求、合并任务、执行尝试、阶段检查点和报告结果须能关联。任务日志记录安全的失败原因、缺失标的、重试预算、下次尝试时间以及为何复用或未发布。不能仅靠一条“处理中”描述诊断中断。终态与飞书状态独立保留。

历史报告、旧任务和投递结果不得为实现刷新而删除或覆盖。上线迁移须能保留旧冻结内容和链接；历史running可经恢复流程判断中断，但不能直接将所有旧running判成功或自动补发。详细字段、保留周期与迁移方案由技术评审提出，本PRD不指定SQL或接口改造代码。
