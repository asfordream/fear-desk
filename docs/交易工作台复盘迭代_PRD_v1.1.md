## 1. 目标与本次决策

面向本人、电脑浏览器、私密使用。用户已明确以独立 FearDesk 复盘项目为统一承载入口，现有云端 FearDesk 保持原状，打通：发现恐慌指标信号 → 标的研究 → 开仓立案 → 关联实际交易 → 逐笔与月度复盘 → 经验规则 → 下次立案检查。富途 OpenD 在本机读取；用户允许交易明细、浮动与已实现盈亏同步到云端，但同步目标与启用时点尚未确定，首版不能默认为已启用云端上传。

复盘回答四个问题：赚亏多少、费用多少、原先为什么交易、执行有什么问题。结果必须可追溯，改进项必须成为下一次能执行、能验证的检查，而非只有总结文字。

用户已确认：2026 年 1 月起历史复盘；每月 3 日北京时间上午 9 点生成上月报告；开仓前填写交易立案；没有历史文字想法记录；新成交自动感知放后续。首版在 FearDesk 统一入口增量扩展，复用已有立案和核算能力，参考开源项目的页面与复盘组织，不以安装演示项目替换现有账本。

本文件更新以下旧范围：9 月 9 日“不做历史迁移”调整为“补齐今年历史复盘”；实时成交感知不作为本次首版验收项。此前研究、策略等模块保留，不因本文件而删除或重写。工具入口已核实为 FearDesk；此前口头工具名称不再作为未决事项。其他工具接入另行定义。

### 4.1 本轮反馈：重做复盘页面，纳入首版

用户明确指出现有问答页面不满足需求：缺少盈亏展示、当时开仓记录和恐慌信号关联。因此本轮包含复盘页面实质重设计，不把展示改造延期，也不以现有问答流程跑通作为复盘交付完成。

主入口为“复盘总览”，采用 Trade Journal 的仪表盘、盈亏日历、交易明细组织方式，结合本项目信号与立案证据。具体分区：

1. 顶部：月份、账户、币种、市场筛选；数据覆盖、核算缺口与审阅状态常驻。
2. 损益区：已实现毛盈亏、净盈亏、发生费用和已实现分摊费用；按原币分别显示。未实现盈亏若资料不完整则展示缺失原因。
3. 日历与趋势区：按市场本地日期展示每日已实现结果，区分已核实无交易、数据未齐与已核算持平；点击日期筛选交易。不把已实现损益累计曲线称为账户净值曲线。
4. 交易表：标的/策略、主信号来源、开平时间、状态、数量、毛净损益、费用、立案有无、复盘进度；可从金额或交易进入证据档案。
5. 交易详情：同屏对照“当时信号与开仓计划”和“实际成交及结果”，下方展示版本时间线、执行差异、复盘记录与改进项。
6. 经验区：重复问题、适用规则、上期动作执行情况；从规则回到来源交易，再从新立案查看该规则。

交易详情必须保存并显示当时恐慌指标值、触发条件、信号/数据时间、开仓理由、预期、风险预算、退出条件及冻结计划版本；显示原始证据和记录时间，避免用今天的信号解释过去的交易。无历史记录时明确未记录，允许单独追加事后回忆。

信号维度统计只使用有来源快照、归属明确且结果可算的交易，给出样本、遗漏数与口径；信号命中后的未交易结果未完整跟踪前，不能把成交样本胜率称为所有信号胜率或信号预测准确率。

问答放在详情的“补充复盘”区域，仍用于判断、策略、执行、风控和改进；不要求先回答问题才能查看已有账务和开仓证据。

## 5. 信号与标的契约

证券身份由提供方、市场、证券类型及代码确定，不能只有 ticker；例如不同市场同代码必须区分。手工输入仍需身份核对；身份未核实可存待确认草稿，不能静默引用另一市场研究。

信号保存不可变快照：来源名称与引用、证券身份、生成时间、实际数据时间、指标值及单位、触发条件、规则版本、原始内容哈希、导入时间、是否过期。保留原始来源规则，本系统不暗中重新解释指标。

从信号创建立案时冻结该快照引用；后续指标更新不改变旧立案。一个信号可关联多份立案，同一交易可引用多个信号；主来源与补充来源分开。保存“观察/暂不交易”及原因，不强制信号都变成订单。

适配顺序：先识别现有恐慌工具的实际输出及身份规则 → 定义只读导入契约 → 联通网页。来源失效时显示时间和缺口，允许手工立案并标明来源。具体工具的路径与接口必须在实现前核实，不能把猜测的文件名当既有接口。

## 6. 开仓立案与经验检查

必填：账户与证券身份、方向/策略、开仓理由、预期持有期、数量及单位、计划价格口径、预算币种与最大可接受亏损、失效条件、退出/止盈/止损安排。期权另记各腿、到期日、行权价、合约身份、乘数来源与到期处理计划。

参考报价、计划约束、实际成交分开；报价时间和数据来源可见。仅计划信息不能证明开仓或平仓。数量、价格、金额明确单位，计算使用 Decimal；缺真实合约元数据不能显示风险已核定。

保存草稿不要求填完；确认立案前校验必填和适用规则。规则无关可填写原因；用户仍决定是否交易。网页检查不能阻止用户直接在富途下单，不能声称券商级强制拦截。

计划确认后冻结版本；修改形成新版本并保存原因、生效与记录时间。首次立案晚于成交时，自动标记“事后立案”。过去交易无法用事后填写证明事前遵守纪律。

经验匹配优先确定性字段：证券/资产类型、市场、策略、方向、期限分组、用户标签；展现匹配原因。只展示用户启用的规则；AI 建议保持待确认状态。

## 7. 实际交易与深度复盘

首版使用按需或月度批量同步、文件导入。系统给出档案匹配候选；按账户、市场、证券、方向、时间及计划腿解释依据。歧义由用户确认，不能只按同代码自动合并。

关联采用成交数量分配；总分配量不得超出实际成交，同一份分配不能重复占用。多腿、部分平仓、移仓与对冲分别记录，不把多次成交简单当成多笔策略。交易/持仓状态以有据事实推进，不能通过拖动看板伪造平仓。

复盘按现有问答流程扩展，覆盖：判断依据、策略选择、执行差异、风险处理、改进动作、本人确认。每条回答关联证据，保存原答和修订。

历史想法默认“未记录”；事后回忆保存回忆内容、记下时间及对应交易，显示“事后回忆”。不得自动推断用户当时的情绪、动机或计划。AI 分析明确区分数据事实、本人陈述和推测；盈利交易同样检查执行问题，亏损不自动意味着违反纪律。

## 8. 核算、费用与报告口径

沿用 v1.0 的账务规则：分账户、市场、证券身份、币种核算，跨月延续未结头寸，明确方向与乘数，FIFO 和生命周期事件有据处理。缺成本不得按零成本算；缺费用不得按零费用算。

月报分别展示：本月已实现毛损益/净损益；本月成交发生费用；分摊入本月已实现损益的费用；未结头寸内尚未确认的费用；利息、分红等非交易项目。不同费用口径明确说明，不能重复扣费。未实现损益仅在历史时点持仓与估值完整时展示，否则缺失。

原币为核算基准；CNY 采用 v1.0 的月末汇率展示口径，缺汇率保留原币并说明缺失范围。无历史净值与外部现金流不展示账户收益率、Sharpe 或回撤。

策略统计采用已确认、完整闭合的生命周期组，和月度账务损益独立展示并提供桥接。统计给出样本和排除数；低样本不宣称已验证优势。未关联立案的历史交易不计为“违反事前计划”，纪律统计分母为具有当时有效计划且可评估的交易。

报告内容：数据覆盖及缺口 → 损益和费用 → 策略与样本 → 代表案例 → 计划/执行比较 → 高频问题 → 已确认改进 → 上期改进执行情况 → 待补证据与下期动作。

报告各维度独立显示状态：数据覆盖、核算、单据核对、策略归类、想法记录、复盘审阅。总状态 DRAFT/PARTIAL/FINAL 以 v1.0 财务质量门槛为基线；缺历史想法不能伪造补齐，也不单独阻止账务核对完成。自动生成不等于本人已审阅。

正式单据需保存文件引用、哈希、覆盖时间与字段映射，不以非空“evidence”文字代替完整证据。核对差额分类：费用口径、跨月分摊、汇率、生命周期、舍入、缺数据；逐项解释并保留未解差额，不能简单放宽误差以通过。

## 9. 今年历史回填

起点固定为 2026-01-01；首次处理截至最近完整自然月。以本文件日期为例，为 1—9 月，10 月为进行中；已生成 9 月人工报告不导致 10 月 3 日重复记账。

先取得年初持仓成本与生命周期资料，或有据证明空仓；不需要给用户生成 2025 年月报，但取得年初成本可能需要更早资料。按月顺序核算，保存持仓结转。不用今天持仓冒充历史期末。

按账户和市场建立覆盖矩阵，不从“本月有成交的账户”倒推出报告范围；无交易月、只有到期事件、仅有费用的月份同样检查。空 API 返回仅表示查询返回零行，需有覆盖证据才标完整。

证券主数据与期初资料按有效时点选择，不能用最新期初记录覆盖所有历史月份。旧 CSV 只有在账户身份、去重与范围核实后方可合并，否则独立展示为待核数据。缺口限制相关证券/统计，仍生成可读草稿并解释排除范围。

## 10. 固定日期自动运行

计划：每月 3 日 09:00，时区 Asia/Shanghai，目标为上一个自然月。首次预期触发为 2026-10-03 09:00，目标 2026 年 9 月。具体成交归属仍按市场本地月份，不按报告发布时间分月。

流程：检查连接 → 同步/导入可用数据 → 查完整性和核算 → 保存报告版本 → 网页显示结果/缺口。缺月结单仍生成草稿，列待办，不伪造 FINAL。

本地持久任务与唯一键约束调度；关闭浏览器不影响任务，电脑关机或休眠不能运行。恢复时列出遗漏月份，按月补跑，单任务执行，避免重复同步和重复通知。连接类故障沿用有限重试，认证/权限/输入缺失保留待处理状态；完成月份只在数据版本变化或显式重算时产生新版本。

区分调度去重键、同步批次和报告内容指纹：重复导入批次不能仅因审计 UUID 不同生成内容相同的新报告。数据或核算版本发生变化，生成新报告并展示差异；旧报告不覆盖。恢复任务必须保证同一月并发触发不重复记账。

此次仅定义产品内调度需求，尚未创建 Codex 自动化或操作系统定时任务。

## 11. 经验规则与追踪

经验实体包括来源交易/报告/证据、问题描述、适用条件、下一次具体动作、检查方式、启用状态、版本、支持案例及反例。状态为建议 → 本人确认启用 → 待验证 → 保留/修订/停用。

例如“某策略开仓前核对事件日程并记录来源”可成为检查项；“更谨慎”不可直接验收。每条动作记录立案时是否适用、是否完成或跳过原因、成交后实际证据和下次复盘结论。

规则必须与当时有效的版本关联，后改规则不把旧交易追判为违规。不能仅因下一笔赚钱就标教训有效；执行情况与交易结果分别记录。此处“记忆”指本地持久经验库，不承诺对所有聊天或券商界面的无条件主动提醒。

## 12. 实施拆分与必要工程决策

| 工作包 | 交付与依赖 |
|---|---|
| T1 基线与接入契约 | 核实恐慌工具、标的身份、当前网页/账本接口；备份与迁移方案 |
| T2 信号与立案 | 不可变信号快照、手工标的、计划来源引用、经验检查占位；复用现有冻结机制 |
| T3 历史与账本 | 年初资料、按时点元数据、完整覆盖、数量分配、单据核对；以 8 月试点再扩展今年 |
| T4 逐笔复盘与经验 | 问答证据、事后标记、规则确认/匹配/执行记录 |
| T5 月报网页 | 损益/费用分口径、策略桥接、质量状态、追溯与版本差异、导出 |
| T6 持久调度 | 月度任务、后台启动、漏跑恢复、并发幂等、失败可见 |
| T7 验收与交付 | 合成端到端、历史连续性、真实数据有据核对、备份恢复、操作说明 |

工程起点为 FearDesk 的 React/TypeScript 与云端 D1、现有本地 FastAPI/SQLite 工作台及 Python 核算模块；以 FearDesk 作为 UI 主体，旧工作台模块作为待提取或适配的能力，不再默认交付独立 FastAPI 前端入口。用户已允许未来同步交易明细及盈亏；具体同步目标、存储迁移与运行契约仍需工程评审，不因旧架构设想而默认已经安装或实现。

建议新增信号快照、信号/立案链接、成交分配、经验规则/检查记录、月度任务/报告索引等实体。金额用十进制字符串，时间存 UTC 并保留市场时区；有效时间和记录时间分开。所有确认与修订复用 expected_version 与幂等请求，数据库写入短事务，核算不绕过源账本。
